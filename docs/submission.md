# Подготовка версии к сдаче

Кейс требует GitHub-репозиторий с историей коммитов и однозначный идентификатор версии на момент дедлайна. Номер приложения `1.0.0` в `package.json` не заменяет хеш итогового коммита.

## Проверка перед коммитом

Из корня репозитория:

```bash
node scripts/check-repository.mjs
npm ci --prefix frontend
npm test --prefix frontend
npm run build --prefix frontend
docker compose config --quiet
docker compose -f compose.yaml -f compose.integration.yaml config --quiet
docker compose -f compose.yaml -f compose.integration.yaml -f compose.gpu.yaml config --quiet
docker compose up --build -d --wait --wait-timeout 60
docker compose exec -T frontend nginx -t
node scripts/smoke.mjs
```

Затем пройти [основной сценарий](../README.md#пошаговый-сценарий-проверки-демо) в браузере. Фактически выполненные проверки и ограничения описаны в [verification.md](verification.md). На GitHub для новых коммитов и pull request настроен [CI](../.github/workflows/ci.yml).

## Что заполняют участники перед финальной сдачей

| Направление | Ответственный | Необходимые материалы |
|---|---|---|
| Frontend | Кирилл | Интерфейс, UI/HTTP-сценарии, адаптер и согласование серверного входа |
| [Backend](../backend/README.md) | Дмитрий | Код, Dockerfile, runtime/lock-файл, сессии, синтетические учётные записи и seed, хранение, миграции, актуальный OpenAPI, тесты и лицензии |
| [ML](../ml/README.md) | Михаил | Код/правила, CPU Dockerfile, модель и манифест, источник/лицензия/хеш артефактов, признаки, метрики, ограничения и тесты |

При добавлении сервисов пройти общий запуск `docker compose --parallel 1 -f compose.yaml -f compose.integration.yaml up --build -d --wait --wait-timeout 180` и сквозной сценарий с реальными серверными сессиями. GPU — дополнительный вариант; базовая версия должна воспроизводиться на CPU. Проверить пиковую память, автономность запуска и сохранение данных. Обновить таблицу готовности в README, архитектуру, THIRD_PARTY_NOTICES и результаты проверки. До этого команда предоставляет жюри автономное frontend-демо и явно указывает состояние остальных компонентов.

## Фиксация и выгрузка

Проверить список файлов и подготовленный diff:

```bash
git status --short
git add .
git diff --cached --stat
git diff --cached --check
git diff --cached
```

В составе должны быть исходники всех готовых компонентов, lock-файлы, Docker/CI, документация, синтетические PDF, миграции/seed и лицензии. `.gitignore` исключает `node_modules`, виртуальные окружения, `dist`, кэши, локальные env/секреты, рабочие базы и uploads, сырые обучающие данные и веса. Проверка репозитория сохраняет положительные примеры для исходников backend/ML, lock-файлов и модельных манифестов; необходимые синтетические fixtures не исключаются.

Для ML-артефактов в Git остаются версия, источник, лицензия, SHA-256 и воспроизводимый скрипт получения во время сборки. Большой игнорируемый файл, который существует только на компьютере Михаила, не является доступной для жюри моделью. Если локальные файлы когда-либо были закоммичены, одно изменение `.gitignore` не удаляет их из истории; текущая проверка отдельно отклоняет отслеживаемые файлы, подпадающие под исключения.

После проверки зафиксировать изменения, отправить их и получить идентификатор:

```bash
git commit -m "feat: prepare Milk Tower prototype for submission"
git push origin main
git rev-parse HEAD
```

Указать полученный полный hash в форме сдачи вместе со ссылкой на репозиторий. Проверить результат CI именно для этого коммита. В приватном репозитории предоставить доступ аккаунту жюри **`alfa-hack-2026`**. Изменения после дедлайна не входят в проверяемую версию по условиям кейса.

Внешнее развёртывание в облаке не подготовлено. Для текущего демо достаточно клонирования и базовой команды Docker; используются роли интерфейса. Для интегрированной версии Дмитрий добавляет синтетические серверные учётные записи и способ входа, а команда обновляет сценарий README. Нельзя указывать старый hash, который не содержит подготовленные файлы.
