# ML — зона Михаила Уляхина

Реализованы детерминированные правила Михаила, объяснения, рекомендация кредитной логики, синтетические компании и небольшой HTTP-сервис. Это не обученная модель и не банковский backend: сервис не создаёт сессии, не сохраняет заявки/файлы и не принимает окончательное решение. Версия правил **1.0.1**, Python **3.12.12** в Docker, сторонних Python-зависимостей нет.

## Запуск и проверка

Из корня репозитория:

```bash
python3 ml/server.py
PYTHONPATH=ml python3 -m unittest discover -s ml/tests -v
```

Первая команда остаётся работать в отдельном терминале на `127.0.0.1:8001`; вторая запускается в другом. Полное демо поднимается через `docker compose up --build -d --wait` и проксирует ML через Nginx. `GET /healthz` возвращает готовность, `POST /score` принимает JSON заявки: `company.inn`, `productId` (`working`/`equipment`), `amount`, `term`, `finances` и `documents[{kind}]`. Контактные данные и содержимое документов не нужны. [Рабочий OpenAPI](../docs/scoring-openapi.json), [примеры запросов](../docs/requests.http).

Ответ: `checks`, `decision`, `message`, `approved_amount` (null без предложения), `positive_factors`, `negative_factors`, `features`, `assumptions`. `decision` — рекомендация, а не изменение статуса заявки. Балл ограничен 0–1000; неактивная регистрация даёт 0. Некорректные входные значения возвращают JSON 422; тело ограничено 64 КиБ. Сервис предназначен только для локального синтетического демо, не для открытого production API.

## Признаки и честные границы

Годовые выручка и расходы делятся на 12. Прибыль — `(revenue - expenses) / 12`. Остаток долга не приравнивается к ежемесячному платежу: демо предполагает погашение за 12 месяцев и добавляет платёж по новой заявке. Долговая нагрузка — `(debt / 12 + loan_payment) / (revenue / 12)`. Ставки соответствуют минимальным ставкам продуктов интерфейса; это допущение, не банковская оценка.

БКИ, регистрация, налоги и динамика выручки берутся по ИНН из `fixtures/mock-companies.json`. Финансы fixtures не перезаписывают анкету. Для неизвестного тестового ИНН используются явно показанные допущения: активная компания, без просрочек и налогового долга, динамика выручки 0%. `documents_provided` означает дополнительный документ после дозапроса; исходные выписка и отчётность бонуса не дают. Содержимое файлов не анализируется.

[Правила](../docs/scoring-rules.md) и [сценарии](../docs/scoring-test-scenarios.md) описывают проверку доменного скоринга на признаках fixtures отдельно от HTTP-преобразования анкеты. Качество кредитного риска на реальных данных не измерялось. Высокая базовая оценка и насыщение на 1000 ограничивают различение благополучных компаний; пороги и бонус за документ требуют дальнейшей проверки Михаилом, а не являются проверенной моделью.

## Подготовленная интеграция

`compose.yaml` уже запускает `ml` на `0.0.0.0:8001`; healthcheck использует Python `urllib`, `curl` не требуется. Порт наружу не опубликован. В текущем демо frontend обращается через `/ml-api/score`, а будущий backend сможет использовать внутренний `http://ml:8001/score`. Согласование серверных ролей и окончательной бизнес-логики остаётся у Михаила и Дмитрия.

Frontend ожидает от backend поле `checks` следующего вида; это UI-контракт, а не требование к типу модели:

```json
{
  "score": 768,
  "rating": "A",
  "recommendation": "Рассмотреть одобрение",
  "factors": [{ "label": "Пример объясняющего фактора", "positive": true }]
}
```

Шкала в предлагаемом OpenAPI — 0–1000. Если модель выдаёт вероятность или другую шкалу, преобразование и смысл рейтинга согласуются с backend. Скоринг предоставляет рекомендацию; итоговое кредитное решение остаётся отдельной бизнес-логикой.

## Контракт контейнера и ресурсы

| Пункт | CPU-режим по умолчанию |
|---|---|
| Сборка | `ml/Dockerfile`, Python 3.12.12, только stdlib, непривилегированный пользователь |
| Вычисление | `ML_DEVICE=cpu`, CUDA скрыта, лимиты 2 CPU / 3 ГиБ, BLAS/OpenMP по 2 потока |
| Запись | Текущим правилам запись не нужна; корневая файловая система read-only |
| Кэш | `/cache` зарезервирован интеграционным Compose для будущей модели; текущий сервис его не использует |
| Модель | Текущие правила не требуют весов; базовый демо-лимит 0,5 CPU / 128 МиБ, интеграционный резерв 2 CPU / 3 ГиБ |
| Автономность | Модель включена в воспроизводимую сборку; работа inference не требует внешнего платного API или скачивания при каждом старте |

Опционально подготовлен [compose.gpu.yaml](../compose.gpu.yaml) для одной NVIDIA GPU. Для его использования Михаил добавляет `ml/Dockerfile.gpu` с совместимым runtime и поддержкой `ML_DEVICE=cuda`. CPU остаётся обязательной базой для обычного ПК. Другие видеокарты могут использовать CPU-режим.

## Что заполнить перед сдачей

| Раздел ML | Заполняет Михаил |
|---|---|
| Подход | Правила / балльная модель / ML, признаки и обоснование выбора |
| Воспроизводимость | Версии runtime и зависимостей, модель, версия, источник, лицензия и SHA-256 артефактов |
| Данные | Происхождение и лицензия; для публичного демо только синтетические данные |
| Качество | Метод проверки, метрики, ограничения и интерпретация факторов |
| API | Вход/выход, endpoint, таймаут, ошибки; согласование с backend |
| Окружение | Измеренные время старта, память и задержка на CPU; GPU — дополнительный вариант |
| Материалы | [Манифест модели](models/README.md), обновлённые THIRD_PARTY_NOTICES и общая архитектура |

Кейс допускает правила вместо сложной ML-модели; ИИ не обязателен. Если используется LLM, по кейсу допустимы только открытые веса. Сырые датасеты, кеши, checkpoints и большие веса не входят в Git. При этом жюри должно получить воспроизводимый способ загрузки проверенного артефакта во время сборки — см. [models/README.md](models/README.md).
