# Выкладка демонстрационной версии

Обычный ПК: `./scripts/run.sh` из чистого Git checkout или распакованного сдаваемого архива. Все сервисы запускаются Docker; приложение доступно только на localhost. Хранение — SQLite в именованном томе. Локальный односерверный MVP не рассчитан на горизонтальные реплики backend.

## Внешний сервер

Подготовлена конфигурация `compose.server.yaml` с HTTPS через Caddy и отдельным паролем для просмотра демо. Для фактического развёртывания нужны Linux-сервер с Docker, домен, DNS на адрес сервера, открытые порты 80/443 и доступ команды к серверу. Внешняя публикация не выполнена автоматически.

1. Скопировать `.env.server.example` в `.env.server`, указать свой `PUBLIC_HOST`.
2. Выполнить `docker run --rm caddy:2-alpine caddy hash-password`; ввести отдельный пароль для демонстрации и записать только полученный hash в `.env.server`, в одинарных кавычках. Пароль передать жюри отдельно от публичного репозитория.
3. Из проверенной версии выполнить:

```bash
export BUILD_COMMIT=$(git rev-parse HEAD)
docker compose --env-file .env.server -f compose.yaml -f compose.server.yaml up --build -d --wait --wait-timeout 180
```

Открыть `https://<PUBLIC_HOST>`; пользователь внешнего шлюза — `reviewer`. Затем внутри приложения выбрать синтетическую роль. Backend и ML не публикуются наружу. Cookie имеет Secure; TLS завершается на Caddy. Это закрытая демонстрация с синтетическими данными, а не промышленная банковская авторизация.

Для `ps`, `logs`, `down` использовать те же `--env-file` и `-f`. Обычный `down` сохраняет БД и сертификаты. Не использовать `down -v`, если нужны накопленные заявки.

## Резервная копия и восстановление

SQLite использует WAL: копирование только `app.db` во время записи недостаточно. Сначала остановить backend (`... stop backend`), затем скопировать весь том `backend-data` в закрытый архив через временный контейнер; запустить backend обратно. Для восстановления остановить backend и восстановить весь каталог `/data` с владельцем UID 10001. Не коммитить БД/сессии и архивы в Git. Для демо допускается восстановление из синтетического seed в отдельном новом томе.

Обновлять сервер следует проверенным тегом/полным hash, перед миграциями сохранять резервную копию. Откат приложения не откатывает схему автоматически: для старой схемы восстановить совместимый snapshot БД. Проверка версии — `/api/v1/version`, версия frontend — `/version.json`.
